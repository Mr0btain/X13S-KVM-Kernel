# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Build/install tooling (bash scripts, kernel patches, a DT overlay) that boots the Lenovo ThinkPad X13s (SC8280XP) Linux at **EL2** for KVM while keeping the DSPs (battery/charging via ADSP `pmic_glink`, audio, USB-C, sensors) working. There is no application code and no test suite; "testing" means booting real hardware and recording results in `notes/boot-log.md`. README.md is the user-facing overview; PLAN.md holds the reasoning, decisions and risks (its "Repo layout" section is stale — trust README's).

## How the pieces fit (boot chain)

1. Firmware boot entry "Ubuntu (EL2 KVM)" → UEFI shell `scripts/el2/startup.nsh` on the ESP (`\EFI\slbounce\`).
2. **qebspil** (UEFI driver) boots ADSP/CDSP/SLPI before ExitBootServices.
3. **slbounce** (needs Microsoft's non-redistributable `tcblaunch.exe`, placed at `out/el2/tcblaunch.exe`) takes over EL2 at ExitBootServices.
4. `grubel2.efi` reads `/boot/grub/el2.cfg`, generated by `scripts/el2-grubcfg.sh` (installed as kernel postinst hook `/etc/kernel/postinst.d/zz-el2-grubcfg`). It picks the newest `*-el2` kernel and builds `/boot/el2/<ver>.dtb` = packaged `-el2` dtb + `dts/x13s-el2-dsp.dtso` overlay, minus the cluster idle state (`cluster-sleep-0`; entering it in s2idle at EL2 hard-resets the machine). Entry 2 is the stock `-generic` kernel at EL2 (KVM only, no DSPs).
5. The patched kernel (`patches/linux/`) *attaches* to the already-running DSPs instead of booting them via PAS (which TZ can't do at EL2). The attach path is selected by `qcom,broken-reset` on the remoteproc nodes `2400000`, `3000000`, `1b300000`, which the overlay sets.

## Build commands

Native arm64 Ubuntu 26.04 (≈8 GB tree, ~65 min on 8 cores):

```sh
scripts/ci-build.sh            # everything (SKIP_APT=1 to skip apt installs)
scripts/fetch-sources.sh       # clones pinned sources from sources.env into src/
scripts/apply-patches.sh       # recreates branch "el2" in $LINUX_DIR from LINUX_TAG and git-am's patches/linux/*
scripts/build-efi.sh           # out/qebspil/*.efi, out/slbounce/*.efi
scripts/build-kernel.sh -j8    # bindeb-pkg -> out/linux-image-*-el2_*.deb (default -j6; ccache if CCACHE_DIR set)
scripts/build-kernel.sh --from-host   # regenerate config/<ver>-el2.config from the running kernel
scripts/build-dtb.sh [base.dtb]       # out/dtb/...-el2-dsp.dtb; verifies broken-reset landed on all 3 DSPs
scripts/package-release.sh     # out/release/ + SHA256SUMS
```

Install (as root, from the **normal EL1 boot**): `el2-install.sh`, `install-esp.sh`, `install-kernel.sh`; each takes `--remove`. `download-release.sh <tag>` fetches a CI release into `out/`.

On-hardware checks at EL2: `dmesg | grep -E "started at EL2|remoteproc.*attached"`, `cat /sys/class/remoteproc/*/state` (expect `attached` ×3). Suspend bisecting: `sudo scripts/suspend-test.sh freezer|devices|platform|shallow|full [--no-modem]` (appends to `notes/suspend-tests.log`; a missing end line means the machine reset).

## Conventions and constraints

- `src/` and `out/` are git-ignored; the repo tracks only scripts, patches, config, dts and notes. Upstream versions/revs are pinned in `sources.env` (sourced by the scripts and CI).
- **Never touch the normal boot path.** Only `\EFI\slbounce\` on the ESP, `/boot/grub/el2.cfg`, `/boot/el2/` and the postinst hook may change; the stock Ubuntu entry and `-generic` kernels stay the default and fallback.
- EFI variables (`efibootmgr`, install scripts) work only from the normal EL1 boot — `qseecom` fails at EL2.
- Kernel patches are `patches/linux/NNNN-*.patch` (git format-patch output). To change them or move kernel versions: update `LINUX_TAG`/`LINUX_DIR`/`KCONFIG` in `sources.env`, run `apply-patches.sh`, fix conflicts in the tree (`git am -3`), then `git format-patch` back into `patches/linux/`, rebuild, and re-test against the checklist in `notes/boot-log.md`.
- Kernel config `config/<ver>-el2.config`: Ubuntu config + `olddefconfig`, `LOCALVERSION=-el2`, no debug info, no Ubuntu signing certs, `QCOM_Q6V5_PAS=m`. The `-el2` suffix is what `el2-grubcfg.sh` keys on.
- Every hardware boot test gets an entry in `notes/boot-log.md` (date, kernel, what loaded, result).

## CI / releases

`.github/workflows/build.yml` runs `scripts/ci-build.sh` in an `ubuntu:26.04` container on `ubuntu-24.04-arm` with ccache. Manual dispatch = build artifacts only; pushing a tag `v<kernel>-el2-<n>` (e.g. `v7.3.1-el2-1`) publishes a release.
